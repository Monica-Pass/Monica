## 问题与修复

用户反馈设置搜索找不到 HyperOS 兼容项。该页面已存在于开发者设置，静态 SettingsSearchCatalog 却未收录；并非大小写匹配故障。修前真实 SettingsScreen 搜索 hyperos 无结果，目录测试也确认没有对应条目，2/2 负向用例按预期失败，runner 4.074 秒。原始回执见 `settings-search-hyperos-329-red-device.txt`。

生产改动仅增加一个 HyperOS 兼容设置搜索条目及静态关键词。收录当前语言的配置诊断、兼容模块、默认密码管理器、保存兼容、减少动画、检测修复后变化及四个兼容模块选项名称，并支持 HyperOS、澎湃、小米、Xiaomi、Redmi、POCO、MIUI、LSPosed、Shizuku 等别名。复用现有字符串资源和匹配规则，不读取任何密码库或账号内容。

结果显示“设置 › 开发者设置”路径，点击定位并高亮既有开发者入口；用户点击入口后仍须按原有流程验证身份，再打开 HyperOS 兼容设置。不会自动开启兼容开关、请求系统权限或跳过验证，也不声称搜索直接深入到受保护子页。认证、导航、设置写入和系统兼容实现均未修改。

## 保留的失败

- `red01` 的两项失败是缺失目录及真实搜索无结果的有效负向对照。
- `main01` 首轮修后设备测试在取消按钮查找失败后，又因后续导航的生命周期异常中断，没有完成整批。`probe01` 保存的语义树证实测试页面使用中文 Context，而 Dialog 自有按钮使用英文 Activity 资源；第二项探针还因重复初始化已存在的合成主密码被拒绝。测试改为读取实际宿主按钮资源，并验证复用已有测试密码，未覆盖或清除测试库。
- `main02` 取消流程已通过。新增原始异常捕获确认，已弃用 Compose 测试规则使用的 unconfined 调度使密码后台读取的继续执行直接到达工作线程，NavController 拒绝非主线程导航，随后销毁时产生次生生命周期异常。测试迁移到项目已有的 Compose v2 规则，沿正常调度队列执行；保留原断言与超时，未修改生产验证或导航。测试的局部 Context 同时保留 ActivityResultRegistryOwner，沿用已有 HyperOS UI 夹具方式。
- 曾误用带 `--tag v1.0.329` 的发布就绪检查，因说明仍标记未发布而被正确拒绝。随后使用适合本次维护的无 tag 元数据检查通过；未创建标签或发布。

前序日志、构建回执、探针语义树和失败堆栈留在本地任务目录。前序 APK 未另存副本，输出已被后续构建覆盖；各次实际哈希保留。最终回执与四份 APK 哈希见 `settings-search-hyperos-329-result.json`。
