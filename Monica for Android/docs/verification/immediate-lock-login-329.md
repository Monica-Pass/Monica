# “立即锁定”登录循环修复（下一版未发布）

## 结论与原因

自动锁定为 0 分钟时有两处会撤销刚完成的认证。设备同步在检查同步开关/配对设备之前读取设置，通用过期检查立即锁回会话；MainActivity 观察到会话解锁、但尚未收到界面认证回调时，重组也会调用有副作用的重新进入检查，再次锁回会话。现分别采用受前台可见性约束的工作会话检查，以及只投影当前认证状态的界面判断。冷启动和 ON_START 仍执行原来的严格会话恢复检查；没有调整密码算法、KDF、密文格式或数据库版本。

用户录屏与日志时钟不同，不作为同一次事件逐秒对照。录屏显示改为“立即”后无法进入；日志无致命崩溃证据。真实旧混淆 Release 的合成库也复现登录回空密码页、进程仍存活。问题属于认证被重复撤销，不以 GPU 告警或 Compose 取消异常推断数据库损坏。

## 实际验证

- main 最终 Debug 主/测试包构建通过（152.894 秒）；23 项相关 JVM 测试全部通过，无跳过。
- MuMu API35/x86_64 最终 20 项设备方法通过（runner 97.683 秒）。完整 MainActivity 用例覆盖同步关闭/开启、错误密码、每次登录后持续 6.5 秒稳定、Activity 退后台再恢复必须重新验证、主动 SessionManager 锁定、原合成记录解密。另含原密码协议、验证取消和迟到结果回归。
- 新实际 R8 Release 构建通过（749.574 秒）。与旧混淆 Release 使用同一隔离包名和本机测试证书，在旧合成库上直接覆盖安装，未卸载/清数据。真实 UI 验证原密码进入、错误密码拒绝、超过同步轮询间隔仍在主界面、按 Home 再回来重新认证、旧记录读取、新建记录、新 PID 冷读，以及旧加密备份实际恢复并保留新记录。独立备份验收期间通过设置将超时改为 5 分钟以允许文件选择器往返，恢复后改回立即并重新验证冷启动登录。
- 最终五个变更路径已按哈希同步回主工作区；四个共享文件两版字节一致，MainActivity 保留平台差异。元数据检查及其 6 项脚本测试通过。329 发布归档与版本配置未改。

## 保留的失败与修正

- main-red01 为预期红测：真实同步观察者用例失败，4 项中 1 失败。
- main-green01 因原生编译并发造成 Windows 资源不足失败；仅为本任务设置 CARGO_BUILD_JOBS=2 后继续。main-green02 构建/JVM成功，但收尾打印触发 GBK 编码异常，实际结果与文件已保存。
- 仅修同步后的 main-device01 为 19/20，复入认证失败；诊断 main-device02 为 0/1。日志证实 MainActivity 重组再次调用 canSkipVerification，修正生产逻辑后 main-device04 整批 20/20；额外复核开发者免验证的首次设置边界后，最终 main-device05 及 fd-device01 再按最终源码整批验证。未删断言、增加超时或修改调度来掩盖失败。
- MuMu 的 Download 映射目录在临时用户及 Owner 下导出均 EACCES；改用 Documents 成功，没有修改存储权限。为缓解内存曾停止本任务实例，MuMu 重启将临时 user13 转为不能前台切换的工作资料，main-device03 因切用户失败没有运行测试；普通版中间验证改用本任务新建 user14；之后因构建内存再次暂停实例，最终重新建立隔离 user15，所有自有用户在收尾移除。
- 普通版备份验收首次驱动沿用 Return/旧导航标签，实际页面为 Back/Pwd，操作前停止；按实际节点修正后继续，无清库或重置。

## 环境清理

最终恢复 Owner 0，仅移除本任务隔离包、自有用户 13/14/15 和合成导出文件；保留原用户 0/10/11/12、配置与数据盘，停止本任务启动的 MuMu 实例 1。实例 0 未操作，AVD 未使用。

## 范围与限制

仅合成数据、MuMu API35/x86_64。旧测试 Release 来自已有 329 混淆构建（本机测试签名、隔离包名），并非用户安装的商店签名 APK。本轮未在用户 HyperOS/Android API37 真机或真实指纹硬件验证，也未进行实际设备间同步传输。设备测试直接触发 SessionManager 主动锁定，不冒充点击锁定菜单的验收。Release 截图受安全窗口保护呈黑屏，已查看但不计视觉验收；功能验收基于真实 UI 操作、节点断言、进程标识与测试回执。详细原始失败与 UI 回执保留在本地任务目录；用户媒体及截图不入库。
