# Bitwarden 旧服务器兼容、Send 返回与同步问题截图（1.0.326）

普通版与 canonical F-Droid 的未发布 1.0.326 修复旧版 Vaultwarden 普通记录被整批拒绝，以及新建 Send 返回时重复弹出导航栈的问题；同步问题弹窗显式跟随防截屏设置，并保留强制保护。普通 versionCode 12、F-Droid 33 不变。

## 根因与改动

旧解析器只接受字符串形式的 legacy `Data`。Vaultwarden 1.30.5 返回 PascalCase 对象，检查的 1.32.7、1.34.3、1.35.0、1.36.0 返回 camelCase 对象；这些正常记录在解密之前就被判为不支持。用户截图中的 Web2026.4.1 是前端版本，公开且无需认证的 `/api/config` 所给 `gitHash=f21a3ada` 对应 Vaultwarden 1.36.0。只核对了公开配置，没有读取用户的 `/sync`、凭据或逐条密文；因此这是高度吻合且已用合成响应复现的兼容缺陷，不是对用户全部记录的逐项鉴定。

`BitwardenCipherDocument` 现在同时接收 legacy 对象和严格解析的 JSON 字符串，保留 casing 规范化、重复键拒绝、typed/common 镜像一致性、未知字段、修订和上传确认。对象来源继续以对象生成更新文档；字符串来源仍保留旧字符串表示。新版 Vaultwarden 不含冗余 `data` 的路径不变。普通类型 1–5 的缺失 typed section、partial、blob、未知类型及损坏密文仍拒绝，不以空记录替换已有本地内容。没有按域名或版本号放行，也没有更改认证、KDF 或密钥算法。

同步服务增加固定结构类别计数（TYPE、NAME、LEGACY_SHAPE、LEGACY_MIRROR、PARTIAL、KEY_ID、TYPE_SECTION）。新增的这条汇总诊断只写类别和数量，不写记录 ID、标题、邮箱、网址或密文，也不自动启用原有可选 forensic/raw 收集功能。

Send 原返回按钮直接调用导航回退；退出动画结束时，仍存活的 `NavBackStackEntry` 又发出 ON_STOP，清理函数再次回退，连下面的主页也弹出。系统返回也会走到该路径。现在返回、保存成功、锁定及后台事件都通过同一个幂等清理入口，先标记撤销，再清空敏感状态、取消编辑工作并只回退一次。提交进行中的返回仍被消费。静态核对确认：保存成功通知在服务器确认和 Room 更新之后发布，草稿提交路径另先清理已提交草稿，不会因退出清理提前取消已确认的持久化。

同步问题弹窗是独立 Window。现在偏好未加载前默认保护，随后按防截屏偏好或已登记的强制保护设置 SecureOn/SecureOff。强制 owner 首次获取和最后释放会通知已经打开的弹窗；弹窗不修改父 Window。MuMu 上修前的三项常规窗口检查本来就通过，不能声称已在模拟器复现用户 OEM 禁截。此次是明确策略及更新时序的防御修复；也不承诺 Compose 重组前后跨窗口零帧延迟。

上游响应模型：[官方 CipherResponseModel](https://github.com/bitwarden/server/blob/6f351999b7a9ac87057d9312a5c7bb6e8edb9f52/src/Api/Vault/Models/Response/CipherResponseModel.cs)、[Vaultwarden 1.36.0 cipher](https://github.com/dani-garcia/vaultwarden/blob/f21a3adae2fbb8582b60b121783c597fe6895ff4/src/db/models/cipher.rs)。

设备服务端夹具按 Vaultwarden 的实际行为忽略上传冗余 data，从 accepted typed/common 字段重新生成响应，验证 GET → PUT → 确认 → 仅清除自有本地投影 → 再拉取。五类测试组合当前支持类型与 Pascal/camel casing，不代表老版本当年提供全部五类。它不是 HTTP 原样回显，也不是真实旧版或官方服务器实例。这里的重新拉取不等于 Android 进程重启。

## 复现、失败与修正记录

- 修前 JVM 两个文档类共 39 项：原 33 项通过，新 6 项中 5 项按预期失败，包含对象解析和 262 条 gate；最终新增第 7 项覆盖固定诊断类别。
- 最初设备夹具遗漏 `isLocked=false`，在认证门控处提前失败；这些运行没有作为格式问题复现。补齐前提后，同一个旧主包对 262 条对象响应明确报出 `Some items could not be synced (262)`；保留损坏数据和锁定负向检查通过。
- 修前真实 NavHost 使用生产进入/退出动画，工具栏返回调用两次，系统返回后 `currentDestination=null`。该批 5 项中导航的 2 项失败、锁定/后台 2 项通过，另 1 项是上述旧同步夹具失败。
- 普通版 fixed01 主包和测试包构建成功；联合 JVM 413 项中 412 项通过，注册测试 `modernRegistrationVerifiesEmailAndSendsDecryptableFreshKeys` 失败。未改该生产/测试代码，同一注册类独立 9 项通过。原失败保留，未把首次联合运行称为全绿，偶发根因未独立查明。
- fixed01 设备 37 项中 24 项通过、13 项失败。新增 262 条首次下载内容核对已经通过；重复同步因夹具初始 canonicalEmail/accountKey 与正常持久身份不一致而失败。补齐身份并每次读取当前 vault；上传断言改为逐项比较发送和接受的自定义字段（包含正常生成的 Monica metadata），没有丢弃字段断言。既有文档测试的过期 schema 82 更新为当前 85。修正后 28 项同步/文档设备测试全部通过。
- 补测 Send 时第一次驱动未正确引用带空格的合成主密码，Android `am` 将其误认作 instrumentation 名称并退出 139；未启动应用测试，不是 Monica 崩溃。仅修本地驱动 shell quoting 后，3 项 Send 实际 UI 保存/草稿测试通过。
- 同批第 4 项既有同步问题入口测试超时：旧脚本未展开现在默认折叠的账号卡。补上账号解锁/报告前提断言和真实标题点击后复测；未修改设置页生产逻辑或扩大超时。
- F-Droid 主编译期间、设备测试 Kotlin 编译开始前，同步了账号卡夹具修正和截图输出到私有目录的调整；单独保存了当时的最终共享文件哈希。生产代码始终匹配该构建启动时的快照。普通版只为这些测试变化重新打包测试 APK，主 APK SHA 不变。
- 原生图片检查发现，仅检查 Window flags 后立即截图仍可得到全黑首帧，故该图片不计作成功截图。测试补上当前弹窗显示及两个窗口均已解除保护的检查，并在 5 秒内要求屏幕 400 个采样点中超过 40 个非黑点；系统栏少量图标不能单独使断言通过。最终图片另外逐张查看，确认标题、说明及按钮实际可见。此处只增强测试和取图时序，生产代码没有再次改动；不把瞬时合成器现象解释为用户设备的持续拒绝截屏。

完整通过/失败方法、构建耗时、APK 标识与 SHA-256、12 个共享文件哈希见同目录 `bitwarden-compat-send-326-result.json`。相关原始设备回执以同前缀保留；更早的构建、失败夹具和完整 JVM XML 在本地任务目录保留。公开材料不包含用户域名、邮箱、日志原件、截图或真实密码库。

## 验证边界

所有设备数据均为隔离包及自有测试用户中的合成记录，设备为已运行的 MuMu API 35/x86_64。验证涵盖五类普通记录、262 条内容和历史、未知字段保留、四种格式编辑往返、修订冲突/坏密文/锁定、真实导航生命周期、弹窗 Window flags 和实际 Send 文本/文件/草稿保存。

本轮没有运行真实官方云或自托管服务器的认证端到端测试，没有用户 Android 17/OEM 真机、R8、所有自构建分支、未来 item 类型或组织/SSO/企业全功能验证。用户截图拒绝问题仍需在其设备确认；此次不能承诺任意未来服务端协议全部兼容。

普通版与 F-Droid 的 326 中英文说明及 F-Droid changelog 33 已同步。图片只留被忽略的 design 目录，不写入仓库或在本文引用。未创建版本标签、Release 或交付 APK。
