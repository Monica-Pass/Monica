## 端口是否相关

原始交换的 endpoint 是相对路径，没有完整服务器主机、协议和端口，不能还原用户配置。HTTP 默认端口 80、HTTPS 默认端口 443 不要求显式填写；自托管使用其他端口且没有反向代理时才需写出实际端口。生产 `BitwardenApiFactory.inferServerUrls` 在自托管地址后追加 `/identity` 与 `/api`，不移除端口。

服务地址的端口和密码条目中网站的端口是两个不同字段。无端口网站本身是有效 URI。两版现有真实 Vaultwarden 1.37.5 上传与独立回读记录，均包含 `http://192.168.123.1` 这一未写端口的登录 URI，共 40 条/版成功，原网址及校验值保留。因此无端口登录 URI 不是已观察到的上传拒绝条件。

422 表示 HTTP 服务已收到请求并拒绝处理；相同服务的 GET 同步 200 也表明接口可达。端口填错通常表现为连接拒绝、超时或访问其他服务。仅凭这两份日志不能排除特殊代理路由错误，但没有证据将本次拒绝归因于缺少端口。

## 根因证据与修复范围

现有本机完整 Vaultwarden 1.37.5 对照中，直连 HTTP、无反向代理，删去 `encryptedFor` 的更新返回与用户相同的 HTML 422；添加 `X-Forwarded-Proto: https` 后仍为 422。两版正确生产请求各上传 40 条成功，独立解密核对各 120 个 URI、匹配模式和校验值。此前 F-Droid 包名标错的证据已作废，重新执行的正确包名结果才计入。

这确认 Monica 存在请求协议兼容缺陷，并支持它解释原反馈；用户实际 Vaultwarden 版本与部署尚未知，不能宣称已经在原实例确认唯一根因。URI 校验缺失另会影响使用条目独立密钥的官方客户端网址显示与匹配，不等同于所有 422 的原因。
