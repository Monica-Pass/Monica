# Keystore startup and retained-data recovery — 1.0.325

> Follow-up on 2026-11-05: actual KernelSU-loaded OMK was subsequently tested in an isolated MuMu clone. See [the separate OMK report](omk-mumu-325.md) for successful recovery scenarios and the failed root-seed-only scenario. The scope statements below describe this earlier alias-replacement experiment.

## Scope and evidence

Ordinary Android and canonical F-Droid, unreleased 1.0.325. Only synthetic data was used on the already running rooted MuMu (Android 15/API 35, x86_64). User 0 and the pre-existing emulator are preserved. Rooted ADB enables observation; no global Keystore reset, ROM modification, real keybox, Magisk/KernelSU/APatch install, or third-party TEE module injection was performed.

The reported 1.0.312 Android 16 stack establishes an AES-GCM authentication failure, public Keystore code 10/internal -30. Without that release's R8 mapping it cannot be attributed to a current source frame, nor does MAC failure alone establish a particular module as the cause. The screenshot's TEESimulator revision cb4044ae4e0b0c2fcdeb63adcb7102df1635ffc1 exists and documents arm64/x86_64 support plus a module manager and private keybox. These tests used MuMu built-in root; no functioning module-manager-based TEE environment was configured or used. The initial package inventory is not a claim that the user environment stayed unchanged during this task. The other screenshot's custom-ROM global-lock/RKP explanation lacks its original trace.

## Changes

- Reuse a successfully accepted encrypted preferences handle, bound to the data directory, recovery selector and keysets. A timeout's late worker result cannot enter the cache. Stale handles reject reads and writes; recovery invalidates process reuse. A cold main-thread constructor fails closed instead of synchronously opening Keystore.
- Prepare secondary Activity/service/keyboard/autofill/credential-provider entries on the bounded startup worker. Direct Boot locked storage is rejected; existing authentication remains required. The ordinary-only system credential export Activity validates its caller before entering the same preparation gate. F-Droid intentionally has no such provider-events entry/dependency.
- Contain Room invalidation backup checks in a coroutine boundary, coalesce outstanding checks, and revoke cancelled work. A real master-key replacement reproduced an uncaught Room → WebDavHelper authentication exception before this change, even with backup disabled.
- Avoid initializing SecurityManager when LAN synchronization publishes non-secret scheduling flags while locked. A real cold :ime launch reproduced an uncaught DeviceSyncCoordinator.pause → publish → SecurityManager authentication exception before this change.
- Bind password-derived and device-unwrapped runtime MDK publication, and data-decrypt completion, to the runtime lock generation. Slow work cannot republish a key after locking.
- A real recovery-button test additionally found Bitwarden startup mirroring safe defaults into the canonical recovery envelope before normal login. The credentials/key/salt were unchanged, but preservation was still violated. Recovered settings mirror only after normal vault authentication; automatic sync and never-lock remain disabled in the independent recovered settings.
- Common-account migration preserves unreadable legacy ciphertext and migration state instead of interpreting a failed read as an empty value. Initial recovery enrollment/write failures do not clear the original field.

No encryption algorithm, KDF, persisted vault format, authentication requirement, or default security level changed. Missing data keys are not automatically regenerated. Unreadable settings, original ciphertext, prior aliases and canonical recovery material are retained. Existing password-protected recovery can recover supported material; direct legacy hardware-key content without independent recovery material cannot be reconstructed after its only key is permanently lost.

## Validation approach

The old warm-constructor probe failed with six provider accesses. The unreadable common-account migration probe failed before its fix by clearing the original C2 username and marking migration complete. A real app-owned AndroidX master alias was then replaced in disposable user 11: opening its unchanged keysets yielded AEADBadTagException/public 10/internal -30 and exposed the two additional unhandled background entry paths above. All failures and original logs remain in the local task directory.

The ordinary seq24 production APK subsequently recovered that same damaged fixture with the original synthetic master password and entered real MainActivity through normal password login. The test checked the original Room ciphertext, decrypted row password, password-wrapped MDK, protected preference, original encrypted preferences file, recovery envelope and aliases. This initial recovery phase invoked ConfirmedStorageRecovery directly; a later fixture strengthens coverage to the actual recovery and second-confirmation buttons. A separate host force-stop/cold launch and password entry also displayed the original fixture row.

The device suite covers missing and replaced C2 keys, bad MDK wrappers, password/native MDK lock interleavings, startup timeout/cancellation/no queued retry, stale selector/keyset handles and editors, secondary-Activity UI responsiveness, recovery cancellation/confirmation, Room backup callbacks and locked LAN status publication. These are deterministic provider/lock fixtures plus actual AndroidKeyStore replacements, not a reproduction of the original ROM hook or hardware TEE.

## Recorded failures and limits

- First ordinary final suite: 86/88 methods passed. The Chrome origin interoperability check failed because com.android.chrome is absent from MuMu, outside this change's storage behavior. The system-back dialog check failed twice because Espresso chose the unfocused base Activity; the corrected test sends the real Android system back key and retains the original cancellation assertions.
- A supplemental JVM run initially failed 11 old protocol fixtures because their existing SecurePreferencesStore shadow did not cover the new prepared-store constructor. Only the isolated Robolectric shadow/configuration was adapted; no production guard or protocol assertion was weakened.
- F-Droid first compile failed after an ordinary-only credential-export file was mistakenly copied. Git confirmed it never existed in F-Droid; only that exact new copy was removed, retaining edition differences. A later test-only compile exposed the absent UIAutomator dependency; the system-back driver was switched to platform Instrumentation instead of adding a dependency. F-Droid WebDAV fixtures then revealed that its existing loopback HTTP opt-in had been overwritten during test copying. Every changed baseline was compared between editions; this was the only additional semantic difference, and its original setup/cleanup was restored with only the new shadow registration retained.
- Root uiautomator successfully wrote fresh hierarchy XML but sometimes exited 139 in its Shutdown thread on MuMu. This was kept as a tool failure, not counted as a Monica crash. FLAG_SECURE made the ordinary recovery screencap black; it is not visual-layout acceptance evidence.
- No Android 16/physical OEM device, real TEESimulator → OMK transition, original user's data, release/R8 build, or permanently lost hardware-only Passkey recovery was validated. Broad claims of complete independence from Android Keystore are not supported.
