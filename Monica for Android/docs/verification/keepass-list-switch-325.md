# KeePass list switching — 1.0.325

Ordinary Android code12 and canonical F-Droid code32 remain unreleased 1.0.325. Final sources and Debug packages were verified on the shared API32 x86_64 AVD using synthetic fixtures.

Both Android editions now tie the selected native list to that database's completed read and asynchronous list computations. Previously the shared list flow and retained grouping kept A visible and clickable after selection changed to B. A deterministic real VaultV2Pane test held the native read mutex for B and found a clickable A in the first Compose frame on the old implementation.

The transition displays a bounded, in-memory title preview: prefer the matching database/filter, otherwise the previous displayed database. Previews carry no record objects, item identifiers, password/OTP values, file handles or mutation callbacks, and have no persistence API. At most four keys retain 80 titles each, capped at 256 characters. They do not enter KDBX save, merge, synchronisation or Room projections. Real list rows are not composed during transition. Empty matching previews stay empty. Lock epochs revoke previews; background/global lock removes them. Only the current foreground selection can finish its UI read.

The breadcrumb area shows the state. After user feedback on verbosity, the usual message is only “加载中…” / “Loading…”. A different source adds “预览：库名” / “Preview: name”; the selected database name already exists in the top bar. Failed reads retain their labelled preview and offer retry. Locked databases hide rows and offer a Monica master-password verification dialog. Successful bounded verification authorises an in-memory read with existing saved credentials, with generation/lock/foreground checks; it does not change those credentials or the KDBX. Password text is not saveable and is cleared on dismiss/request replacement/background. No biometric flow was added.

Both the vault pane and legacy password pane use the selected native snapshot for passwords and supplementary notes/cards/documents/addresses/OTP/passkeys. Filtering/grouping readiness gates real item callbacks. Non-native and archive paths retain their prior inputs. Old editor revision checks, read-only checks, source preflight and original-file mutations remain in place.

The status owns a single 260 ms height animation, with outgoing sensitive content immediately removed. The local Canvas sketch was inspected, then revised and inspected again after the user asked for shorter text. Eight strings cover all 18 resource configurations. Screenshots/sketches remain in ignored docs/design only.

## All-view loading and stack order

The All view observes existing SyncTaskRunner queued/running KeePass, Bitwarden and MDBX work, deduplicated by provider/database. Passwords/TOTP compatibility work and remote work for the same KDBX count once. The display reads only task metadata; it does not schedule a read, synchronisation, write or unlock. Initial/asynchronous list preparation also shows Loading…. More than one known active database displays Loading… · N vaults. This is a count of active databases, not a completed/total percentage. An unknown batch has no invented total. Finished, failed, blocked, conflicted and canceled tasks do not keep a loading spinner alive; existing error/authentication handling remains separate. Lock/background removes the loading indicator. A running transfer/delete retains priority.

The old group score puts favorites ahead of card type (favorite adds10; single/stack type adds1–3), so the favorite single shown in the user screenshot can precede nonfavorite stacks. The final password-page list stably partitions all multi-entry password groups and mixed manual stacks before ordinary single items. Each subset keeps its previous order (including its existing favorite/title/manual ordering), and entry ordering within a stack is unchanged. No group metadata, sortOrder or source database is written. The separate VaultV2 view already renders individual rows by design and keeps that behavior.

The local All-view Canvas was inspected before native implementation. Its archived editable JSON and screenshot remain in ignored docs/design/keepass-list-switch-325. Native status tests drive actual coordinator requests held by synthetic gates and verify two databases → one → completion, leaving All, local computation and application lock. A separate VaultV2 status test covers 1.5 font scale, no text clipping and breadcrumb restoration. Stack order is checked through the real final list builder; these checks do not constitute a full production-account multivault sync or a whole-Activity stacked-list screenshot.
