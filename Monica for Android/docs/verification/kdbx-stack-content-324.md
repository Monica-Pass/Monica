# KDBX stacking and add-content validation — 1.0.324

Status: both distributions passed final validation; unreleased. Applies to ordinary Android and canonical F-Droid. Published 323/323b and existing Wi-Fi changes are retained.

## Root causes and repair

The password page saved stack metadata one selected entry at a time. With existing editor drafts, its first write changed the KDBX revision and a subsequent member used the earlier revision. The original seq06 Debug APK reproduced a native-editor revision conflict in the actual ViewModel selection command (three-method negative control, 19.836 seconds, one failure). The other two original-APK methods passed custom-field and complete content/attachment round trips, so inability to encode Monica metadata was not the cause.

Stack actions now validate every selected native identity before any write and commit each database selection together using its current list snapshot. Only the two stack fields change. Original native field values/protection, unknown fields, attachments, UUIDs and original KDF/format are preserved. Existing editor drafts remain unchanged so old editing sessions still cannot overwrite the result. The error uses the existing localized storage-save message instead of a token error.

The actual add-content UI also exposed a second revision conflict: creating an additional credential after saving the first entry advanced the file before deferred embedded content was published. Explicit final publication now compares that destination against its saved draft, including lossless fields/protection, history, attachment references, presentation properties and parent. Only an unchanged destination can use the current snapshot for this final step. A changed/deleted/moved/locked destination is rejected; current file revision validation still runs during the write. Ordinary editor saves keep their original conflict rule. The first complete UI save and all exact value assertions then passed, but resaving the restored account group exposed the same per-account writer problem. Native project targets now stage every account with distinct custom fields, including multiple new rows whose temporary IDs are zero, and commit the rows together. During editor load, sibling drafts explicitly adopt the primary entry opening snapshot only if its source revision and lock version still match; a changed load blocks saving. They are not refreshed at the Save action. Attachment copying and explicit removal follow the existing safety order. If a later destination or attachment step fails, successful native batches are retained rather than rolled back through stale individual editors; originals are not removed before all destinations accept every row. This is per-file safety, not a cross-file transaction guarantee.

## Test scope

The new backend suite covers all three stack modes and repeated changes, a single file commit per selection, unchanged passwords, stale editor rejection, denied writes, invalid selection, external revisions and locking. It also covers custom text/hidden/unknown fields, five block kinds (API key/token, SSH, GPG, QR), long Unicode chunks, four embedded wallet kinds, address/contact supplemental fields, order metadata, payment/OTP fields and byte-identical native attachments after editing, stacking and explicit process-cache eviction.

The real Compose menu test adds note, bank card, document, address, text/hidden custom fields, five block kinds and an additional credential, then saves and reopens/resaves the same original KDBX. It waits for the existing title and persisted GPG content to render before resaving, rather than treating the empty form shell as completed loading. Its attachment was first inserted through the native attachment service, then opened/retained through the UI; this is not a system file-picker acceptance test. It checks exact secrets and generated GPG key material, protection flags and attachment bytes, and ensures original KDBX passwords are not projected into Room.

Two native project regressions verify one-commit updates with distinct protected/unprotected fields, new accounts and preserved attachments, and no partial update on denied writes. Two publication regressions exercise a sibling credential save followed by successful publication, and a changed destination followed by list refresh/lock with unchanged disk bytes after rejection.

## Intermediate failures

The first menu fixture did not compile because a disk assertion helper was not suspend; only its signature was corrected. The initial UI execution requested unsupported GPG 2048-bit generation before rendering; the fixture now uses the existing supported 3072-bit option, without weakening production policy. The next actual menu run reached final save and exposed the second production issue (117.795 seconds, menu failure and existing editor test passed). A subsequent UI run passed its initial save and all value/byte/protection assertions but timed out on resave (94.527 seconds); this triggered the native project batch repair and two additional regression methods. After the batch patch, the menu resave was still rejected (94.551 seconds): only the primary entry had acquired a new editor baseline. Sibling enrollment and a fixture wait for actual loaded content were added. These failed runs are retained separately and are not counted as passing final results.
