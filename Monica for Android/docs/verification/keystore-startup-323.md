## Follow-up: TEE/keybox and non-returning hook calls

The user supplied a further historical observation: another user reportedly crashed after switching from a module called "teers" to "omk", then could enter after clearing application data. The names and versions of the two current reporters' modules remain unknown. Clearing data is not a data-preserving repair. It removes the old encrypted store and can allow a fresh initialization; that observation is consistent with incompatible or unavailable old keys, but also with other stale application state. It does not identify which component changed the key or prove keybox certificates themselves are the encryption key.

The following independent boundaries were inspected:

- Monica's startup master key uses AES-256-GCM via `MasterKey.Builder.setKeyScheme`. It does not request an attestation challenge, Google online verification or StrongBox. The actual cached AndroidX Security Crypto `1.1.0-alpha06` source leaves `mRequestStrongBoxBacked` false unless requested. The separate biometric data key intentionally requires authentication; the compatibility data key does not. Neither is an attestation certificate/keybox.
- Android's [Keystore documentation](https://developer.android.com/privacy-and-security/keystore) and [key-attestation documentation](https://developer.android.com/privacy-and-security/security-key-attestation) describe different operations: protected key use versus verification of an asymmetric key's provenance. Passing online integrity/attestation does not establish that an existing AES key decrypts Monica's encrypted preferences.
- "teers" could refer to [TEESimulator-RS](https://github.com/saschazepter/TEESimulator-RS), but that identity is not confirmed. At inspected commit `6d241e56d6e8146cd67ed4ac3dadc9c632969549`, its README describes injection into `keystore2` and Binder interception. Its [`KeyMintSecurityLevelInterceptor`](https://github.com/saschazepter/TEESimulator-RS/blob/6d241e56d6e8146cd67ed4ac3dadc9c632969549/app/src/main/java/org/matrix/TEESimulator/interception/keystore/shim/KeyMintSecurityLevelInterceptor.kt#L695) can forward an ordinary AES request to hardware or generate a module-owned software AES key when force-generation is configured. Its operation handler routes generated keys from its own registry. Therefore a targeted application can depend on module-specific key handling, even without requesting attestation. The inspected implementation already supports AES; an unsupported-AES bug must not be assumed for this version.
- The related upstream project has a [historical AES generation report, #189](https://github.com/JingMatrix/TEESimulator/issues/189), explicitly showing an integrity check passing while a symmetric-key operation fails. It is closed, and the maintainer states that the 4.0 reference backend should resolve that case. The [maintainer's response on #305](https://github.com/JingMatrix/TEESimulator/issues/305#issuecomment-6302090171) also acknowledges earlier parameter-passing faults affecting Gatekeeper. These are independent evidence that such modules can affect more than certificate verification, not proof that either Monica reporter has those particular bugs. No module was installed, disabled, downgraded or configured during this investigation.

## 2026-10-30 production startup hardening and covering-update verification

At the user's request, the existing unreleased Android work was committed **before** changing production security code: normal checkpoint `2ac92c96f8`, canonical F-Droid checkpoint `5d3a9971`. This distribution's checkpoint is `2ac92c96f8`. The earlier statements above that production code was unchanged describe the 2026-10-29 investigation only; this follow-up implements and tests the program boundaries described below.

### Fixed boundaries

1. A dedicated daemon executor retains **one actual startup-operation slot**. The caller waits at most **15 seconds**, including retry serialization, rather than awaiting completion of an uninterruptible provider call. Cancellation promptly releases the UI wait. A timed-out native/Binder operation continues occupying the slot until it really exits; repeated retries return `SECURE_OPERATION_IN_PROGRESS` instead of queueing work or creating threads. Timeout returns `SECURE_OPERATION_TIMEOUT`. Existing bounded retries for ambiguous reads and no-overwrite preflight checks remain.
2. Only the caller that accepts a successful result can publish maintenance readiness. Timeout/cancellation locks the session and clears runtime unlock state. A late worker result cannot enable maintenance, and a failed attempt prevents background maintenance from automatically reopening storage in that process; an explicit startup retry is required. A guarded context/preferences/editor prevents subsequent preference operations after an abandoned call eventually returns, including fluent editor chains.
3. Recovery availability is checked inside the same bounded worker. `MainActivity` uses that result instead of synchronously reacquiring the recovery lock after a timeout. A real-activity test holds the actual application recovery lock: the blocked screen and retry action remain reachable after the deadline while the lock is still held.
4. C2/V2 data reads and MDK-wrapper reads use **existing** AndroidKeyStore data keys. Missing keys raise an existing-key failure instead of calling a get-or-generate path. Failed wrapper reads retain the original `mdk_keystore_blob` and password-recovery material. Wrapper-unavailable state requests the existing password reentry flow; wrapper repair uses the original password-authenticated MDK. Ordinary `UserNotAuthenticatedException` expiry retains its existing authentication behavior rather than being marked as a damaged wrapper.

No encryption format, KDF, database migration format or recovery transaction strategy was changed. No automatic ciphertext clearing, lost-key replacement, plaintext fallback or automatic password recovery was added. Diagnostic additions report exception types and reason codes, not passwords, keys, codes or arbitrary provider messages.

The guard does not terminate a native operation already entered or roll back its effects; its purpose is to prevent subsequent preference operations and publication after abandonment. A process kill/native crash remains outside application exception handling. The deadline does not prove the affected module will return or that its keys still decrypt the original data.
