# Keystore startup and data preservation — 1.0.323

Date: 2026-10-29. Normal development build, unreleased.

The initial two reports were reviewed: an application crash after changing keybox and including Monica in a module's scope, and a startup hang that reportedly cleared after a Google online check. Neither initial report includes an application version, Android version, module configuration or crash trace. The user has already confirmed that these details are unavailable. The latest instruction is to investigate as far as practical, report unresolved cases explicitly, and prioritize existing users' data. Later screenshots are assessed separately below.

Source inspection covered `MonicaApplication`, `BaseMonicaActivity`, `MainActivity`, `SecureStorageStartup`, `SecurePreferencesStore`, session initialization, autofill-grant initialization and the recovery entry point. No Google online integrity/attestation check or anti-hook startup check was found. The application and base-activity initialization reviewed here do not open the encrypted preferences before the main secure-storage check. This does not establish what external modules do to the process or system calls.

The existing secure-storage check runs on the IO dispatcher. It retries only ambiguous read failures, at most three times, and repeats the no-overwrite preflight each time. Missing keys, incomplete keysets and authentication failures block startup. They do not trigger preference clearing, replacement of lost master keys or a plaintext fallback. Database and attachment maintenance is gated on successful secure-storage preparation. The blocked screen offers retry, a diagnostic containing types/codes rather than sensitive values, exit, and password recovery when an existing recovery envelope is available.

Verification on the reused `Monica_Issue136_API_32` AVD (`emulator-5582`):

- 16 existing secure-storage/startup device tests and two recovery-screen device tests passed. These cover transient and persistent read errors, missing/corrupt key material, unchanged encrypted preferences, diagnostics, and reachable recovery actions. They ran alongside three boarding-pass tests; the combined log ends with `OK (21 tests)`.
- `LocalVaultRecoveryInstrumentedTest` (14 tests) and `ConnectionRecoveryInstrumentedTest` (four tests) passed together: `OK (18 tests)` in 174.867 seconds.
- The additional tests exercise password, OTP, attachment CEK and Passkey preference recovery; incorrect passwords and corrupt envelopes; password rotation; interrupted mirroring/migration; concurrent writes; stale-manager rejection; and recovery after losing a recovered generation's key.
- Connection tests verify KeePass and MDBX unlock forms and native file contents, WebDAV/Bitwarden credentials, offline caches and pending sync state. Recovery does not enable cloud writes.

The tests use isolated synthetic fixtures, uniquely prefixed preference stores and test recovery aliases. Their cleanup does not delete the application's default master-key alias. Raw logs are retained locally under `.codex-tmp/startup-keyboard-323/`: `boarding-secure-normal-device.txt` and `keystore-data-preservation-normal-device.txt`. No personal database or credential fixture was used.

The reported module environments could not be reproduced. Existing exception handling cannot resolve a hook that terminates the process or keeps a synchronous native/Binder call from returning. In the latter case, the current splash can remain visible indefinitely. A coroutine timeout alone does not guarantee cancellation of that call, so no timeout followed by opening or resetting the vault was introduced. These reports remain unconfirmed and are not claimed as repaired. No production security code, encryption policy or stored user data was changed as part of this investigation.

## Follow-up: TEE/keybox and non-returning hook calls

The user supplied a further historical observation: another user reportedly crashed after switching from a module called "teers" to "omk", then could enter after clearing application data. The names and versions of the two current reporters' modules remain unknown. Clearing data is not a data-preserving repair. It removes the old encrypted store and can allow a fresh initialization; that observation is consistent with incompatible or unavailable old keys, but also with other stale application state. It does not identify which component changed the key or prove keybox certificates themselves are the encryption key.

The following independent boundaries were inspected:

- Monica's startup master key uses AES-256-GCM via `MasterKey.Builder.setKeyScheme`. It does not request an attestation challenge, Google online verification or StrongBox. The actual cached AndroidX Security Crypto `1.1.0-alpha06` source leaves `mRequestStrongBoxBacked` false unless requested. The separate biometric data key intentionally requires authentication; the compatibility data key does not. Neither is an attestation certificate/keybox.
- Android's [Keystore documentation](https://developer.android.com/privacy-and-security/keystore) and [key-attestation documentation](https://developer.android.com/privacy-and-security/security-key-attestation) describe different operations: protected key use versus verification of an asymmetric key's provenance. Passing online integrity/attestation does not establish that an existing AES key decrypts Monica's encrypted preferences.
- "teers" could refer to [TEESimulator-RS](https://github.com/saschazepter/TEESimulator-RS), but that identity is not confirmed. At inspected commit `6d241e56d6e8146cd67ed4ac3dadc9c632969549`, its README describes injection into `keystore2` and Binder interception. Its [`KeyMintSecurityLevelInterceptor`](https://github.com/saschazepter/TEESimulator-RS/blob/6d241e56d6e8146cd67ed4ac3dadc9c632969549/app/src/main/java/org/matrix/TEESimulator/interception/keystore/shim/KeyMintSecurityLevelInterceptor.kt#L695) can forward an ordinary AES request to hardware or generate a module-owned software AES key when force-generation is configured. Its operation handler routes generated keys from its own registry. Therefore a targeted application can depend on module-specific key handling, even without requesting attestation. The inspected implementation already supports AES; an unsupported-AES bug must not be assumed for this version.
- The related upstream project has a [historical AES generation report, #189](https://github.com/JingMatrix/TEESimulator/issues/189), explicitly showing an integrity check passing while a symmetric-key operation fails. It is closed, and the maintainer states that the 4.0 reference backend should resolve that case. The [maintainer's response on #305](https://github.com/JingMatrix/TEESimulator/issues/305#issuecomment-6302090171) also acknowledges earlier parameter-passing faults affecting Gatekeeper. These are independent evidence that such modules can affect more than certificate verification, not proof that either Monica reporter has those particular bugs. No module was installed, disabled, downgraded or configured during this investigation.

Two additional deterministic device tests now exercise the production startup boundary with isolated encrypted preferences:

1. A provider exception wrapping `KeyPermanentlyInvalidatedException`, `UnrecoverableKeyException` or `KeyStoreException` reaches the blocked result, stops after the existing three ambiguous-read attempts, leaves ciphertext unchanged, keeps the session locked and keeps maintenance disabled. Diagnostics include exception types and exclude injected secret messages. These tests inject errors at the context/preference read boundary; they do not emulate a real vendor TEE or certify the exact KeyMint phase on a modified phone.
2. A controlled non-returning synchronous read keeps the startup continuation pending while the main dispatcher still runs. Cancelling its coroutine does not complete the worker until the test releases the read. The test releases its own latch in `finally`, confirms that no further read occurs after cancellation and confirms unchanged encrypted preferences. This reproduces the indefinite-wait mechanism, not the reporters' module installation. Native process termination remains outside an application's exception handler.

Both test APKs rebuilt successfully (ordinary: 4m 57s; F-Droid: 3m 27s). The complete startup/recovery-screen suite passed in each distribution: **20 tests** each, ordinary `Time: 28.996`, F-Droid `Time: 13.86`. The test source has matching SHA-256 hashes across distributions; the secure-storage production implementations match after normalizing line endings. Production security and startup UI were left unchanged: no software fallback, key replacement, preference reset or automatic recovery was added. The concrete remaining limitation is a provider/Binder call that never returns; the available evidence does not justify declaring either real-device crash fixed. Additional build/device logs are retained locally under `.codex-tmp/keybox-feedback-323/`.

## Follow-up: fifth report and AlwaysStrong Inject v1.0.5

The user later reported a fifth affected person and supplied a module screenshot showing **AlwaysStrong [Inject] v1.0.5**. The Monica version is only presumed to be the latest; no new exception trace or confirmation of direct process exit versus the recovery screen is available. The user explicitly clarified that screenshots two and three describe much older reports that may already have been addressed. They are historical context, not additional confirmed reproductions on the current version.

The older conversation screenshot contains a crash report for **Monica 1.0.312-26091612-01**, versionCode 12, Android 16/API 36, dated 2026-09-16. It reports `javax.crypto.AEADBadTagException`, caused by `android.security.KeyStoreException: Signature/MAC verification failed`, with internal Keystore code **-30** and public code **10**. This establishes an authenticated-decryption failure in that historical build. It does not distinguish changed key material, damaged ciphertext or module/provider behavior. Its application frames are R8-obfuscated; no mapping for that exact build was available, so the frames are not assigned to current source lines. The fifth person's failure is not assumed to have this stack.

The original [AlwaysStrong v1.0.5 release](https://gitlab.com/Evokerr/AlwaysStrong/-/releases/v1.0.5) and source at tag commit `72309a7c5117f28f44a1cd72b89ff1c5302208bf` were inspected read-only:

- [`module/module.prop`](https://gitlab.com/Evokerr/AlwaysStrong/-/blob/72309a7c5117f28f44a1cd72b89ff1c5302208bf/module/module.prop) defines v1.0.5 and the five authors shown in the screenshot; the [Inject override](https://gitlab.com/Evokerr/AlwaysStrong/-/blob/72309a7c5117f28f44a1cd72b89ff1c5302208bf/module-variants/inject/module.prop.override) defines the matching name. Matching metadata identifies a relevant upstream version; it does not certify the installed binary or its configuration.
- The [build script](https://gitlab.com/Evokerr/AlwaysStrong/-/blob/72309a7c5117f28f44a1cd72b89ff1c5302208bf/build.sh) pins **TEESimulator-RS v6.0.1-307**, shared across the release variants. Inject additionally pins PlayIntegrityFix v4.9-inject-s. The [tagged README](https://gitlab.com/Evokerr/AlwaysStrong/-/blob/72309a7c5117f28f44a1cd72b89ff1c5302208bf/README.md) describes Binder interception inside `keystore2`. Inject is not merely a fingerprint change that leaves the Keystore layer out.
- [`module/build_target_txt.sh`](https://gitlab.com/Evokerr/AlwaysStrong/-/blob/72309a7c5117f28f44a1cd72b89ff1c5302208bf/module/build_target_txt.sh) includes user-installed packages by default, permits explicit per-app exclusion and distinguishes auto, generate (`!`) and leaf-hack (`?`) modes. This makes application scope/mode relevant, but the fifth person's actual settings remain unknown.
- The pinned engine's [`KeyMintSecurityLevelInterceptor`](https://github.com/Enginex0/TEESimulator-RS/blob/v6.0.1-307/app/src/main/java/org/matrix/TEESimulator/interception/keystore/shim/KeyMintSecurityLevelInterceptor.kt) handles AES requests and can select module-owned software generation when generation is forced. It also persists symmetric keys and explicitly documents why AndroidX MasterKey/EncryptedSharedPreferences need that persistence across reboot. Therefore this version must not be described as lacking AES support or lacking symmetric-key persistence. Neither the screenshot nor this source proves that a key was lost on the affected phone.

Third-party AlwaysStrong/OhMyKeymint forks were encountered during discovery, but their seed-reset or other recovery behavior is not attributed to this original Inject release. External installation, reset and cleanup instructions were not executed. No module was installed or switched, and no module files or application data were changed.

Current Monica startup already wraps authentication failures from opening the encrypted keyset/preferences, returns `Blocked`, keeps the session locked and preserves the encrypted store. The existing synthetic authenticated-keyset regression and the earlier 20-test startup/recovery suite cover this boundary. They do not establish that every later business-data decryption path is covered or reproduce a modified Android 16 phone. No new production security change or additional device run was made for the screenshots alone. The fifth report remains **unconfirmed and not claimed as fixed**; the practical missing evidence is its actual failure stack or reproducible module environment, already reported unavailable. Existing encryption and data-preserving recovery remain in place.
