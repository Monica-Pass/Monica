# 旧数据保护升级：迁移入口与实施边界

状态：1.0.331 已实现显式确认的主密码独立恢复后端，已完成[限定范围的升级与故障验收](../verification/password-recovery-331.md)。正常安装继续使用原 Keystore 路径；本文中的全库盘点、首次升级提示、迁移恢复点与自动迁移仍是候选设计，未接入生产。

## 当前确定的范围：保留正常路径，补强主密码兜底

保留 Keystore 的正常保护与快捷解锁用途，不进行面向所有旧用户的默认后端切换。单独完善原主密码恢复链路，要求在原 alias 丢失、同名异钥以及整个 Keystore 不可用时，都能验证受支持的普通本地数据；恢复本身不能强制依赖创建新系统密钥。

这降低了正常路径与集中升级的影响范围，但不意味着零迁移：仍只有旧设备密钥才能解密的历史内容，需要在可读时建立独立保护。仅新增恢复按钮或 README 提示不能实现这一点。恢复验收必须覆盖全部已声明范围，并明确未检查、不可读和硬件不可导出项目，不以抽样结果宣称“全部数据”。

已实现的后端直接认证现有恢复封装并恢复原 MDK，不先打开 Keystore 配置或生成系统密钥。候选加密配置落盘并读回验证后才发布独立 selector；原配置、recovery.json、数据库和 alias 保留。取消、锁定和超时撤销发布权限；冷进程需要原主密码，随后仍需正常入口认证。密码后端暂不开放生物识别修复或重置全部数据，以免把不可用的设备密钥重新变成强制依赖。

密文分类已集中到 LocalCipherEnvelope，迁移使用与读取一致的外层空白规则，未知格式继续保留。恢复后附件服务按实际配置句柄更新缓存，旧操作仍由原安全检查拒绝。此项修复不等同于下文的全库盘点或“所有历史数据已保护”证明。

## 首次升级提示可以采用，普通备份恢复不能直接充当迁移

升级后首次正常解锁，可以检查是否存在需要处理的旧数据，再显示保护升级入口。提示由实际数据状态驱动，不按安装版本写一个永久的 `migration_done` 标记。用户稍后处理、进程中断、导入旧数据或读取失败后，都应能够重新检查。

现有 `BackupRestoreApplier` 面向备份导入：包含去重、源 ID 到目标 ID 映射、关系重建和明确的本地替换模式。`BackupContentPolicy` 中的便携备份还会移除原生库/云端身份，避免恢复副本继续写回原来源。这些是备份恢复的用途，不能把它们当成原库内部完全保真的加密迁移。

升级流程只更换必要的加密封装及经过验证的历史密文，不重新创建逻辑项目。保留原 MDK、记录 ID、UUID、时间戳、同步身份、保护位、未知字段、历史和附件关系。硬件不可导出的密钥继续单列，不能用主密码封装替代其语义。

## 用户可见的流程

1. 正常认证后检查数据与空间。登录成功和配置恢复成功分别不代表历史数据已经全部可读。
2. 展示需要迁移、无法读取、未检查及硬件绑定的数量与范围。未知格式或检查中断不能计入完成。
3. 用户启动保护升级后，先创建一致、加密、落盘读回验证过的恢复点。原库继续保留；失败不开始迁移。
4. 转换可验证的旧密文，并在提交前核验会话、源值和实际持久化的新值。取消/锁定后停止，保留可继续检查的状态。
5. 用密码独立恢复的 MDK 进行全量复核；清楚报告残留项。全量复核不等于已经拥有离机备份。

首次提示允许“稍后”。未完成保护升级时不能禁止用户导出可读数据、检查故障或正常使用仍可读的记录。也不能强制迁移后立即删除旧 alias 或原文件。

## 防止重复实现与长期债务

- 密文识别与真实解密保持一致，包括明确格式外层的空白；只在一个位置定义格式判定。普通明文中的空白保留。
- 盘点和迁移共用字段范围与格式处理，业务页面不各自维护“已迁移”状态。
- 迁移记录和完成证明绑定数据/凭据修订与检查范围；新数据、外部变化或未知类型撤销相应证明。应用版本只记录来源，不充当完成证据。
- 主密码后端复用现有 MDK、版本化 KDF 和认证加密封装。以统一存储后端与启动状态机接入；不让主界面、输入法、自动填充各写一套临时降级逻辑。
- 先实现并验证可继续检查的迁移，再接一次性提示。不能先承诺“已保护全部数据”再补扫描范围。

## 备份与恢复点各自的证明

迁移恢复点应保留完整原始存储状态及关联文件，处理 SQLite WAL 和多存储一致性；它用于本次变更失败后的保留/恢复，不能冒充独立便携备份。恢复时还必须拒绝覆盖迁移后用户的新修改。

便携备份必须验证无源安装 alias 的新环境能还原对应的数据与关系。现有完整备份遇到不可读字段仍应失败；保存原始密文的保全包可以另提供，但必须说明它不保证能够解密，也不能把跳过不可读字段后的产物标成完整成功。

## 密码后端的切换条件

密码解锁应从有界的版本化封装直接恢复原密钥和加密配置，不能先依赖 AndroidKeyStore 打开配置，也不能在恢复后强制创建新的 Keystore alias。生物识别等快捷解锁作为可选路径。

候选后端必须落盘读回验证后才发布 selector；旧配置、原密文和旧 alias 保留。新格式必须让不了解它的旧包明确拒绝，不能误认成空库或继续使用过期凭据。当前旧代码只识别 UUID 形式的恢复 selector，因此不能仅加一个会被旧包忽略的 `backend` 属性就认为回退安全。普通版实际旧330 Release已验证拒绝该格式且材料保留，回到331可读；F-Droid旧代码以Debug验证，实际旧Release被Android版本号检查拒绝安装，不能混称为相同验证。

系统入口必须分别验收：主应用、冷启动自动填充、独立 `:ime`、凭据提供方和后台任务。取消、锁定、凭据变化、进程重启后不能接受迟到的授权或解密结果。

## 本次实施的验收门槛

完整矩阵见[安全存储审查](keystore-resilience-audit-331.md)。首次升级提示不是放宽门槛的理由：实际旧 Release 的同包同签名 R8 覆盖升级、全旧数据/新写入/冷启动/独立恢复、故障保留和版本回退仍须分别验证。仅有调试包单元测试不能接入默认迁移。

永久丢失且无独立封装的随机旧密钥无法由备份或新版本补造。预防措施应在旧数据仍可读时完成，并明确报告未能保护的部分。
