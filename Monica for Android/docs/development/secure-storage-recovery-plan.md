# 密钥环境变化的软件恢复方案

状态：新增界面、状态诊断和独立恢复演练已实现于未发布 1.0.331；本轮实测范围及保留失败见 [验证报告](../verification/secure-recovery-331.md)。核对日期：2026-11-23。

## 目标与已知事实

用户补充：出现 `MISSING_MASTER_KEY / PREFLIGHT` 的用户停用 OMK 后已经恢复正常。后续目标是让用户遇到密钥环境变化时，在 Monica 内获得明确、可执行的处理流程，尽量通过原主密码恢复使用。

这次恢复正常支持“原密钥仍可用、当前访问路径受环境变化影响”的解释，不应按永久丢钥处理；仍没有证据能判断该用户当时为什么没有主密码恢复按钮。不能将此前人为暂移合成恢复文件的复现描述成用户文件被 OMK 删除。

已有 MuMu 真实 OMK 实测表明：独立恢复材料完整时，在新的可用密钥后端中进行主密码确认恢复可成功；旧记录、新写入和不同进程冷读写通过。详见 [复现报告](../verification/omk-startup-missing-master-331.md)。本方案复用该能力，不设计应用自动改 OMK 作用范围的 Root 功能。

## 实施前的能力与缺口

| 位置 | 已有能力 | 需要补齐 |
| --- | --- | --- |
| `SecurityManager.ensureMdkInitializedWithPassword` | 成功验证原密码后尝试 `localRecovery.enroll`；可选升级在提交前失败时保留原凭据并允许健康旧库登录 | 用户看不到“能登录但恢复准备未完成”的状态；当前主要是日志记录 |
| `LocalVaultRecovery.enroll` | 生成密码保护的独立恢复材料；写入前校验；保持凭据代次和修订一致性 | 复用已有材料的分支核验 snapshot，但未执行一次完整的“只凭当前主密码解开独立恢复材料”演练；不能把结构可读等同于独立恢复已验证 |
| `LocalVaultRecovery.available` | 有界启动检查期间判断恢复文档是否可读取 | 缺失、撤销、格式错误、不支持版本等都折叠为 false，故障页和复制诊断无法说明原因 |
| `MainActivity.completeSecureStartup` / `SecureStorageRecoveryScreen` | 有材料时显示主密码输入、恢复按钮及二次确认；失败保留原数据 | 无材料时只剩通用说明与重试、复制诊断，没有针对密钥缺失和恢复材料状态的行动说明 |
| `LocalVaultRecovery.recover` / `ConfirmedStorageRecovery` | 验证原主密码和原 MDK；另建配置并读回核验后切换，保留原配置；取消、超时撤销发布权限 | 应复用该事务和授权边界，不能新增静默重建原 alias 的快捷路径 |

## 应用内流程

### 1. 正常使用时准备并验证恢复能力

在用户成功输入原主密码后，沿现有 enrollment 流程维护恢复材料，并增加不写入生产存储的独立恢复演练：从恢复文件取出密码封装，使用刚验证的主密码解开 recovery key、配置 snapshot 和 MDK，核对当前凭据 generation/revision、所选存储及原 MDK 一致。任何一步失败都不标记为“已验证”。

验证使用有界后台 worker，不能在主线程执行 KDF、文件锁或 Keystore 调用。只在本次前台授权仍有效、凭据与修订仍匹配时发布结果，临时密码和密钥不持久缓存；锁定、后台、取消或换库后撤销迟到结果。

安全设置显示三类明确状态：

- **恢复保护已验证**：说明本次原主密码已完成独立恢复演练，显示验证时间。这个状态不保证文件以后不会损坏，也不保证所有设备硬件凭据都能恢复。
- **需要输入主密码完成准备**：适用于旧安装尚未登记、一直使用指纹而没有完成密码验证，或改密后明确需要重新登记的状态。
- **恢复保护未就绪**：说明无法建立或验证独立材料；提供重试和现有加密备份入口。若原库本身健康，保持原正常解锁行为，不因为可选准备失败把用户锁在应用外。

不新增较弱的口令派生算法，不把密钥另存为明文，也不以“存在一个 JSON 文件”显示绿色就绪。已有材料损坏或存在改密/修订冲突时，不擅自覆盖，沿现有事务边界报告失败。

### 2. 启动失败时进入明确的修复页面

将结构性恢复检查从 Boolean 扩展为可诊断状态，至少区分：未检查/超时、未登记或文件缺失、明确撤销并需重新登记、无法读取/无效内容、不支持版本、可尝试主密码恢复。最后一项仅意味着可以尝试，真正解密仍由密码验证决定。

页面按实际错误与状态提供动作：

| 条件 | 说明与动作 |
| --- | --- |
| `MISSING_MASTER_KEY` 且材料可尝试恢复 | 显示“当前系统密钥不可用，可尝试使用原主密码恢复”；进入现有二次确认流程 |
| `MISSING_MASTER_KEY` 且没有有效材料 | 明确显示无法提供原密码恢复的原因；引导恢复创建该库时的原密钥环境，或在另一安装验证独立加密备份 |
| 原密钥环境恢复 | 点击重新检测，重新执行有界启动检查；成功后返回正常登录，登录后核验恢复保护 |
| provider 超时、存储尚未解锁或操作仍进行中 | 显示对应等待/系统解锁/重试说明，不误报密钥被永久删除，不并发堆积 worker |
| 原材料或凭据代次不一致 | 保留原文件并提示一致性问题，不删除 generation/revision，不自动接受旧密码或旧恢复副本 |

OMK 只作为“近期更改系统密钥环境”的排查示例，错误本身不能证明安装或使用了 OMK。普通应用没有标准 Android API 可以指定绕过模块、直接访问被隐藏的 System 后端。作用范围操作应由用户在模块界面完成；应用不申请 Root、不自行停用整个模块。

### 3. 在当前可用环境中修复，随后重新认证

用户输入原主密码并明确确认后，复用现有恢复事务：解密并核验独立材料，保留原库和原配置，在当前后端创建单独的新配置，完成真实读回验证后才切换选择器。失败、取消或超时不发布新选择器；不将一次输入主密码直接变成后台的长期登录授权。

恢复成功后返回正常登录页。用户再次登录后可继续使用；指纹仍需按现有明确确认流程重新绑定。当前后端如果连新密钥生成/读回也不能完成，必须报告恢复未完成，不能显示成功。

### 4. 没有材料时保留退出路径

如果原密钥与独立恢复材料都不可用，应用内说明原数据仍保留，提供备份恢复说明和复制诊断。第一阶段不在启动阻断页直接覆盖导入备份，避免未打开的旧库被混合或覆盖；继续采用另一安装验证备份的路径。

不能承诺在密钥及所有恢复材料已经永久丢失后，单凭主密码还原随机生成的数据密钥。软件方案的关键是提前准备、真实验证和故障时的明确引导。

## 诊断与维护边界

复制诊断增加无敏感内容的恢复状态分类及是否完成检查；保留现有 store、code、phase、attempts。不要输出密码、密钥、完整恢复文件、记录标题或原始异常消息。检查留在有界 worker 内，不在失败页重新获取可能被阻塞的文件锁。

优先实施一轮完整闭环：状态分类与诊断、原密码验证后的恢复演练、正常设置中的准备状态、启动故障页的对应动作。复用现有加密备份；本轮方案不引入第二套自制恢复文件格式，也不把自动选择旧副本作为恢复策略。旧副本可能包含已经撤销的密码，必须保持现有改密和回滚保护。

普通版与 canonical F-Droid 同步维护共享实现和文案，保留平台差异。实施时按仓库要求准备本地界面草图、全部受支持语言和大字号验证。

## 验收条件

1. 旧安装用原主密码登录后，只有完整独立解密演练通过才显示已验证；未准备、无法写入或演练失败均有明确提示，健康旧库仍能正常登录。
2. 同一合成库 System → 真实 OMK，以及 OMK → System 两个方向，分别覆盖有效恢复材料、缺失、损坏、撤销、未知版本和当前后端不可用；错误不得全部归类为文件缺失。
3. 实际故障页输入错误密码被拒绝；正确密码与二次确认恢复后原密文仍在，旧记录可读、新记录可写，不同 PID 冷启动再次通过。
4. 取消、返回、锁定、后台、超时、并发设置写入、改密和恢复事务中断后，不发布迟到授权、不接受旧密码、不偷偷更换原 alias 或清库。
5. 用旧版实际 R8 Release 创建合成数据，以同包同签名的新 Release 覆盖升级，验证原密码、原记录、新写入、加密备份恢复及冷启动；两版 Debug 回归不能替代 Release 升级验收。
6. API 35/x86_64 MuMu 可作为真实模块复现环境；用户 API 37/ARM64 真机未验证时必须保留该限制。截图只放本地忽略目录，提交仅含文字证据。

本文件保留设计目标与验收清单；实际通过、基线失败和未覆盖项以本轮验证报告为准。自动演练仅在主应用密码登录成功后运行，已有材料只读核验；手动补齐仅适用于健康旧安装或允许重新登记的状态，不绕过现代凭据的发布标记。
